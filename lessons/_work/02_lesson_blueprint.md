## 1. 과정 전체 이야기

8개 교시는 서로 다른 예제를 늘리지 않고 개인정보가 없는 합성 영수증 한 장을 끝까지 발전시킨다.

```text
샘플문구점
거래일자: 2026-07-27
연필 2개 × 1,000원 = 2,000원
노트 1개 × 3,000원 = 3,000원
합계: 5,000원
```

```text
필드 정의
  → 준비된 OCR 결과 확인
  → 텍스트 정제
  → JSON 구조화
  → Gradio 화면
  → 처리 함수 통합
  → 검증과 CSV
  → 사람 검토를 포함한 업무 적용
```

공통 구현 기준:

- 각 Colab은 새 런타임에서 독립적으로 위에서 아래까지 실행한다.
- 기본 경로에는 API 키, 실제 OCR 모델, 외부 문서 다운로드가 필요 없다.
- 실제 EasyOCR는 선택 셀로 제공하고, 생성형 AI API는 연결 전 준비사항만 확인한다.
- 새 핵심 개념은 교시당 최대 3개다.
- 교육용 도식은 교시당 2개다.
- 형성평가는 교시당 2문항을 기본으로 한다.
- 확장 실습, 제품 비교, 모델 학습, 배포, 데이터베이스는 제외한다.

## 2. 1교시 — OCR보다 먼저 정할 것

> 영수증에서 무엇을 꺼낼지 정하고 전체 Document AI 흐름을 한 문장으로 설명한다.

### 핵심 개념

1. OCR은 문자를 읽는 단계이고 Document AI는 구조화·검증·활용까지의 전체 흐름이다.
2. 처리 전에 필요한 필드와 자료형을 먼저 정한다.
3. 오류 영향이 큰 필드는 사람이 확인하도록 표시한다.

핵심 문장:

> 자동화는 문서를 AI에 넣는 일에서 시작하지 않고, 어떤 값을 왜 꺼낼지 정하는 일에서 시작합니다.

### 비유

OCR은 영수증을 읽어 주는 눈이고 Document AI는 읽은 내용을 장부에 옮기고 틀린 값까지 확인하는 사무 담당자다.

한계: 실제 시스템은 사람처럼 완전히 이해하지 않고 모델과 규칙으로 값을 예측하고 검사한다.

### 60분

| 시간 | 내용 |
| --- | --- |
| 0~5분 | 합성 영수증과 최종 미니 앱 소개 |
| 5~17분 | OCR과 Document AI 차이, 5단계 흐름 |
| 17~25분 | 필드 정의 시연 |
| 25~48분 | 필드 정의 실습 |
| 48~57분 | 결과 비교와 형성평가 |
| 57~60분 | 다음 교시 연결 |

### 실습

- 기본: `store_name`, `date`, `items`, `total_amount`의 자료형·필수 여부·사람 검토 여부 작성
- 대체: 이미지 대신 동일한 텍스트 영수증 사용
- 코드: `FIELD_SPEC` 딕셔너리와 JSON 저장
- 산출물: `field_spec.json`

### 도식

1. 영수증 → OCR → JSON → 검증 → CSV의 5단계 지도
2. 합성 영수증의 상호명·날짜·품목·합계 영역 표시

## 3. 2교시 — OCR 결과를 눈으로 확인하기

> 준비된 OCR 결과를 원본 영수증과 비교하고 틀린 글자를 찾는다.

### 핵심 개념

1. OCR 결과는 텍스트, 위치, 신뢰도를 포함할 수 있다.
2. 흐림, 기울기, 잘림은 결과에 영향을 준다.
3. 신뢰도는 정답 보장이 아니라 확인 순서를 정하는 참고 신호다.

핵심 문장:

> OCR 결과는 정답지가 아니라 컴퓨터가 읽어 본 초안입니다.

### 비유

OCR 결과는 학생이 칠판을 받아 적은 노트와 같다.

한계: 신뢰도는 시험 점수나 정답 확률과 같지 않으며 엔진마다 의미가 다를 수 있다.

### 60분

| 시간 | 내용 |
| --- | --- |
| 0~5분 | 필드 복습 |
| 5~17분 | 텍스트·위치·신뢰도 |
| 17~27분 | 원본과 OCR 결과 비교 시연 |
| 27~50분 | 바운딩 박스 표시 실습 |
| 50~57분 | 오류 찾기와 형성평가 |
| 57~60분 | 다음 교시 연결 |

### 실습

- 기본: 준비된 `ocr_result.json`과 완성된 `draw_boxes()`로 결과를 확인하고 텍스트 저장
- 대체: 노트북 안의 `MOCK_OCR_RESULT` 사용
- 선택: EasyOCR 실제 실행
- 제공 코드: `load_ocr_result()`, `draw_boxes()`
- 학습자 작성 범위: 결과 텍스트를 줄 단위로 합쳐 저장
- 산출물: `ocr_text.txt`

### 도식

1. 바운딩 박스·인식 텍스트·신뢰도가 연결된 OCR 결과 해부도
2. 같은 영수증의 정상 이미지와 기울어진 이미지 비교

### 형성평가

1. 높은 신뢰도만 보고 정답으로 확정해도 되는가?
2. OCR 오류를 만들 수 있는 문서 상태 두 가지는 무엇인가?

## 4. 3교시 — OCR 초안을 정돈된 데이터로 바꾸기

> OCR 텍스트를 원문을 훼손하지 않으면서 헤더와 품목 행으로 정리한다.

### 핵심 개념

1. 문서는 키-값과 반복 항목으로 나눌 수 있다.
2. OCR 줄 순서가 사람이 읽는 순서와 다를 수 있다.
3. 정제는 표현을 정돈하는 일이지 원문에 없는 값을 만드는 일이 아니다.

핵심 문장:

> 정제는 새로운 답을 만드는 것이 아니라 이미 읽은 내용을 찾기 쉽게 정리하는 과정입니다.

### 비유

OCR 텍스트는 장바구니에 섞인 물건이고 정제는 종류별 바구니에 나누는 작업이다.

한계: 복잡한 표는 단순 줄 나누기만으로 복원되지 않을 수 있다.

### 60분

| 시간 | 내용 |
| --- | --- |
| 0~5분 | OCR 오류 복습 |
| 5~17분 | 키-값과 반복 항목 |
| 17~27분 | 정제 전후 시연 |
| 27~50분 | 영수증 텍스트 정제 |
| 50~57분 | 원문 보존 확인과 평가 |
| 57~60분 | 다음 교시 연결 |

### 실습

- 기본: 공백과 금액 쉼표를 정리하고 헤더·날짜·품목·합계 줄 구분
- 대체 입력: 노트북에 포함된 `SAMPLE_OCR_TEXT`
- 코드: 일부가 완성된 `normalize_line()`, `group_receipt_lines()`
- 결과에는 `raw_text`, `cleaned_lines`, `change_log`를 함께 보존
- 산출물: `clean_receipt.json`

### 도식

1. OCR 원문과 공백·줄바꿈만 정리한 결과 비교
2. 영수증의 헤더·날짜·반복 품목·합계 구조 지도

### 형성평가

1. 정제 중 원문에 없는 값을 추측해도 되는가?
2. 품목이 단순 키-값과 다른 이유는 무엇인가?

## 5. 4교시 — 필요한 값만 JSON으로 담기

> 필드 설계에 맞춰 영수증 값을 JSON으로 만들고 원문에 없는 값은 `null`로 처리한다.

### 핵심 개념

1. 스키마는 필드명, 자료형, 필수 여부를 정한 데이터 설계도다.
2. 원문에 없는 값은 추측하지 않고 `null`로 둔다.
3. JSON 문법 통과와 값의 사실성 확인은 서로 다른 검사다.

핵심 문장:

> JSON 모양이 맞는 것과 영수증 내용이 맞는 것은 별개의 문제입니다.

### 비유

JSON 스키마는 빈 신청서 양식이고 추출은 영수증에서 찾은 값을 각 칸에 옮겨 적는 일이다.

한계: 양식의 칸이 모두 채워져도 내용이 정확하다는 뜻은 아니다.

### 60분

| 시간 | 내용 |
| --- | --- |
| 0~5분 | 정제 결과 복습 |
| 5~17분 | JSON과 스키마 |
| 17~27분 | `null`과 근거 확인 |
| 27~50분 | JSON 구조화 실습 |
| 50~57분 | 스키마 확인과 평가 |
| 57~60분 | 다음 교시 연결 |

### 실습

- 기본: 제공된 스키마 골격의 날짜와 합계 필드를 완성하고 mock 결과와 대조
- 대체: `extracted_result.json` 사용
- 선택 확인: Colab Secrets와 조직 데이터 처리 조건 등 API 연결 전 준비사항
- 제공 코드: `mock_extract()`, `validate_schema()`
- 학습자 작성 범위: 스키마 골격의 두 필드와 `null` 규칙 확인
- 산출물: `receipt.json`

### 도식

1. 영수증 네 영역과 JSON 필드 연결
2. JSON 문법·자료형·원문 근거의 세 가지 확인문

### 형성평가

1. 원문에서 찾지 못한 값에는 무엇을 넣는가?
2. JSON Schema를 통과하면 내용도 정확한가?

## 6. 5교시 — Python 함수에 화면 붙이기

### 핵심 개념

2. 버튼 이벤트는 입력값을 함수에 전달하고 반환값을 출력에 표시한다.
3. 화면과 처리 함수는 분리한다.

핵심 문장:

> Gradio는 새로운 AI를 만드는 도구가 아니라 이미 만든 Python 함수에 화면을 붙이는 도구입니다.

### 비유

Gradio 화면은 리모컨이고 Python 함수는 실제로 동작하는 기계다.

한계: 보기 좋은 버튼이 처리 함수의 정확성과 안전성을 보장하지 않는다.

## 7. 6교시 — 작은 함수들을 한 줄로 연결하기

> 업로드, OCR 결과 선택, JSON 구조화를 하나의 처리 함수로 연결한다.

### 핵심 개념

1. 단계를 작은 함수로 나누면 오류 위치를 찾기 쉽다.
2. 각 단계의 상태를 화면에 표시한다.
3. mock 전환 사실을 숨기지 않는다.

핵심 문장:

> 통합은 큰 함수를 만드는 일이 아니라 확인한 작은 함수들을 순서대로 연결하는 일입니다.

### 비유

문서 처리는 바통을 넘기는 이어달리기다.

한계: 운영 시스템의 복잡한 재시도와 병렬 처리는 이번 과정에서 다루지 않는다.

### 60분

| 시간 | 내용 |

| 5~17분 | 함수 분리와 상태 |
| 17~27분 | 성공·mock 전환 시연 |
| 27~50분 | 통합 처리 함수 |
| 50~57분 | 실패 경로와 평가 |
| 57~60분 | 다음 교시 연결 |

### 실습

- 기본: 제공 보조 함수를 `process_document()`에서 연결
- 대체: 오류를 먼저 표시하고 학습자가 `샘플로 계속`을 선택한 뒤에만 `SAMPLE_OCR_TEXT`, `SAMPLE_JSON` 사용
- 화면의 상태에는 항상 `LIVE 선택 경로` 또는 `MOCK 결과`를 표시
- 선택: EasyOCR 어댑터
- 코드: `validate_upload()`, `process_document()`
- 산출물: `app_06.py`

### 도식

1. 기본 경로와 mock 전환 흐름
2. 파일 확인·OCR 모드·JSON 생성 상태 표시 예

### 형성평가

1. mock 사용 사실을 표시해야 하는 이유는 무엇인가?

## 8. 7교시 — 틀린 값을 걸러 CSV로 저장하기

### 핵심 개념

3. 검사를 통과해도 중요한 값은 사람이 원문과 비교한다.

핵심 문장:

> 검증은 AI가 맞다고 선언하는 과정이 아니라 사람이 확인해야 할 문제를 눈에 보이게 만드는 과정입니다.

검증 함수는 정해진 규칙에 걸리는 항목을 찾는 공항 보안 검색대와 같다.

한계: 검색대를 통과해도 내용의 의미와 목적까지 모두 올바른 것은 아니다.

## 9. 8교시 — 자동화의 마지막 단계는 사람의 확인

> 미니 앱의 전체 흐름을 점검하고 실제 업무에 적용할 한 장짜리 카드를 만든다.

### 핵심 개념

1. 자동화 후보는 반복량, 오류 영향, 예외 빈도를 함께 본다.
2. 개인정보, 외부 전송, 접근권한, 보존·삭제를 확인한다.
3. 최종 승인자와 오류 수정 절차를 정한다.

핵심 문장:

> 앱이 실행되는 것은 개발 완료이고 누가 결과를 확인하고 책임질지 정하는 것이 업무 자동화의 완료입니다.

### 비유

Document AI 앱은 신입 사원이고 사람 검토자는 최종 결재자다.

한계: 모든 값을 사람이 다시 입력하게 만들지 않도록 검토 범위는 오류 영향에 맞춘다.

- 대체: 제공된 실행 결과를 읽고 문제 지점과 검토자 표시
